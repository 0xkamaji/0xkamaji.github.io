The one import is `mscoree.dll`:  

<div class="focus-block">

Mscoree.dll is a Microsoft library file that is part of the Microsoft .NET Framework, essential for running applications that use managed code. It is located in the C:\Windows\System32 folder and is required for the execution of .NET applications. 

</div>
	
We also see in the Data Directories a ".NET Header" with an address and size and, when I attempted to debug the binary I was prompted to install a .Net framework. These all pointed me towards this being a .NET binary which I therefore loaded in `dnSpy`.

Pretty quickly I came across the following function `btnDecode_Click()`:


This function appears to access a stored resource named dat_secret and enters into a decoding loop. The function has 3 separate loops that takes the result of each loop and feeds it into the next.

## Challenge 3

This challenge gives us a file named such_evil. Running file shows the following. 

```
such_evil: PE32 executable (console) Intel 80386 (stripped to external PDB), for MS Windows, 2 sections
```

So we load the binary in our analysis tools. Looking at the file in PE-Bear it definitely appears to be stripped or possibly packed. IDA gives a similar warning, but loads the start point. 

<figure>
  <img src="/assets/images/posts/Flare_on_2014_challenge3/ida_packed_warning.png" alt="Ida Packed Warning">
  <figcaption>Ida Packed Warning</figcaption>
</figure>

From here we see local variables loaded for a call to `sub_401000`. Jumping to this function we see a lot of mov instruction moving data one byte at a time. From here I jump into my debugger x32dbg with the intention to follow this data being built on the stack.

As I step through the function it begins loading information byte by byte using the `eax` register to load the data byte by byte and then loading that byte into memory locations starting at `ebp-201`. I follow this memory location via a dump and finally continue to the end of this memory writing process where we see this memory address loaded into eax and then a call is made to eax!

```
00402495 | 8D85 FFFDFFFF            | lea eax,dword ptr ss:[ebp-201]          |
0040249B | FFD0                     | call eax                                |
```

While we could export the function from this dump and load in our debugger I assume this would be a simple function returning our flag in a few instructions. Instead we step through multiple loops using various keys for xor'ing data to reveal quirky strings.

Finally, after stepping through many decryption looks we reveal the flag in memory:

  <img src="/assets/images/posts/Flare_on_2014_challenge3/flag.png" alt="Flag in mem">
  <figcaption>Challenge3 Flag</figcaption>
</figure>

The flag is - `ch.5h311010101@flare-on.com`
